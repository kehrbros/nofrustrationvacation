# Multilingual support (i18n)

- **Languages:** German (`de`, source language) and English (`en`). Every visible text in the frontend exists in both languages.
- **Binding:** always add new or changed UI texts to `de.ts` **and** `en.ts` in the same change. Do not write texts directly in components, helper functions, `aria-label`, `title`, `placeholder` or error messages.

## Structure

- Library: [i18next](https://www.i18next.com/) without React binding, instance in `frontend/src/i18n/index.ts`.
- Texts: `frontend/src/i18n/de.ts` (source) and `frontend/src/i18n/en.ts`, one object per language, organised by area (`trips`, `booking`, `payment`, …), shared texts under `common`.
- **Type-safe:** keys are typed (`i18next.d.ts`), `t('gibt.es.nicht')` does not compile. `en.ts` has the type of `de.ts`: a missing or additional key does not compile either.
- Test `src/i18n/i18n.test.ts` additionally checks for identical keys, identical placeholders and no empty texts.

## Usage

- `import { t } from '../i18n';` in components and helper functions alike, e.g. `t('trips.title')`.
- **Placeholders:** `{{name}}` in the text, values as an object: `t('trip.deleteStop', { name: stop.name })`. Both languages use the same placeholders.
- **Plural:** keys with `_one` and `_other`, call with `count`: `t('common.stops', { count })` → "1 Stop" / "3 Stops".
- **Enumerations instead of lookup tables:** enum values as sub-keys, e.g. `` t(`incident.type.${type}`) ``. No tables with texts at module level, they would not be recomputed when the language changes.
- **Emphasis:** `<b>…</b>` in the text and output with `<Rich text={t('…')} />` (`src/i18n/Rich.tsx`), never set as HTML. Links in the middle of a sentence: split the text into parts before and after the link.
- **Formats:** format numbers, prices and dates only via the language, never with a fixed `'de-DE'`:
  - `formatMoney`, `formatNumber`, `locale()` from `src/i18n`.
  - Date and time via `src/trips/time.ts` (system time zone) or `src/bookings/localTime.ts` (local time of the accommodation); ranges with `Intl.DateTimeFormat#formatRange`.
  - Locale: `de-DE` or `en-GB` (day before month, 24 h).
- Texts entered by the user or coming from data (names of trips, stops, hotels, descriptions of incidents) are not translated.

## Language selection

- Order: stored choice (`localStorage` `nfv.language`), otherwise system language (`navigator.languages`, first German or English one), otherwise English.
- Switch in the profile menu (`LanguageSwitch`), applies to this device only, not stored on the server.
- On change the app is re-rendered (`LanguageRoot` in `main.tsx`), open dialogs stay because they are part of the URL. Also sets `<html lang>`.
- The language also switches: antd locale (`de_DE`/`en_GB`), language of the PayPal button (`locale` in the SDK URL), language of the place search (Photon `lang`).

## Backend

- The frontend sends the language as `Accept-Language` to `/api/v1` (`src/api/apiClient.ts`).
- Texts generated by the backend that appear in the UI are not translated yet: reasons from the ranking of alternative accommodations (`candidate.reason`), error messages of the IdP (login page, consent). Exception: the backend error page (`templates/error.html`) is German/English via `messages.properties`/`messages_de.properties` and `Accept-Language`. The frontend renders the agent's proposals itself from numbers, see [advisor.md](advisor.md#frontend).
- The PWA manifest (`vite.config.ts`) and `index.html` stay German, the manifest only supports one language.

## Tests

- Tests run in German (`src/i18n/testSetup.ts`, `setupFiles` in `vite.config.ts`), independent of the machine's language, and check the German texts.
- English is spot-checked in `src/i18n/i18n.test.ts` (`i18n.changeLanguage('en')`, then back to German).
